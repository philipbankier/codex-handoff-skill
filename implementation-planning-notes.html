codex-handoff 1.2.0 Implementation Planning Notes

These notes track how the implementation plan interprets or tightens the approved design spec at docs/superpowers/specs/2026-06-20-codex-handoff-1-2-0-design.md. They include plan-level decisions; artifacts assigned to later tasks remain planned until those tasks create them.

Design Decisions

  • The plan treats the existing Claude Code/OpenClaw skill as the stable surface and creates a separate Codex direct skill under the Codex plugin. This avoids recursive codex exec behavior inside Codex.
  • The Codex direct skill gets its own references instead of symlinking to the Claude references. The two paths share concepts, but their runtime instructions differ enough that duplicated small reference files are safer for 1.2.0.
  • The release verification command is planned as scripts/verify-release.sh, not a package-managed test harness. This matches the repo rule against adding app code or build tooling.
  • The eval fixture is planned as evals/evals.json only. The release gets test cases for future evaluation, not a custom runner.
  • The eval fixture uses plain JSON cases instead of a runner so 1.2.0 gains testable scenarios without adding a custom harness.
  • The stable Claude path now gets its own escalation reference so users see the same escalation vocabulary before they try the experimental Codex path.
  • The plan includes an explicit stable-path escalation reference at skills/codex-handoff/references/escalation-policy.md even though the spec emphasizes the direct Codex path. This keeps both surfaces aligned on escalation vocabulary.
  • scripts/verify-install.sh is included in Task 1 because the plan listed it as an existing refresh diff and Task 1 verification scans scripts for stale patterns, even though the original staging command omitted it.
  • The plan includes cleanup of examples/simple/README.md because it still teaches stale automatic-execution and sentinel behavior that conflicts with 1.2.0.
  • Task 2 marketplace metadata was corrected to the current Codex source schema after local CLI verification, and the plugin path is repo-root relative at ./plugins/codex-handoff-codex.
  • Task 6 stores final release evidence in docs/releases/1.2.0-verification.md so reviewers can see exact command exits and concrete verification limits without rerunning the full checklist.
  • Task 6 treats ASCII normalization as mechanical cleanup across tracked scanned files. The broad stale-literal scan still reports the untracked release plan under docs/superpowers/plans/, which is outside the allowed edit scope.
  • Philip approved treating docs/superpowers/plans/ as off-limits planning input rather than release output for the final stale-literal scan.
  • The pre-merge audit follow-up promotes install-verifier regression checks and Codex plugin install smoke into scripts/verify-release.sh because release evidence should not rely on one-off manual proof.
  • The canonical GitHub repository for docs and plugin metadata is philipbankier/codex-handoff-skill; the old philipbankier/codex-handoff URL redirects but is treated as stale release metadata.
  • The install verifier now treats a detected OpenClaw config directory with no codex-handoff skill as a failure, while keeping the no-OpenClaw-detected case as a non-failing skip.
  • The release verifier distinguishes rg exit code 1 for no matches from other scan errors so stale-pattern and secret scans cannot pass on tool failure.

Deviations From The Spec

  • No intentional product-scope departures. The implementation plan keeps Grok, GLM, MCP, hooks, Claude plugin packaging, app code, package.json, and public marketplace publishing out of 1.2.0.
  • The plan treats exact Codex marketplace install commands as verification-time facts, not hardcoded assumptions. Local help shows codex plugin marketplace add|upgrade|remove, but workers must still check the active CLI before documenting commands.
  • The plan allows the existing unstaged documentation refresh to be incorporated instead of restarted. The worker must review the diff and preserve good changes while completing the 1.2.0 scope.

Tradeoffs

  • Separate Codex and Claude skill trees create some duplication, but avoid runtime confusion and make each skill readable by the agent that will actually execute it.
  • The Codex plugin duplicates some stable-path references because direct Codex execution must not inherit Claude supervisor wording or call codex exec recursively.
  • A small eval fixture is less powerful than a real harness, but avoids adding a dependency surface to an instruction/script repository.
  • A shell release verifier is less expressive than a Node or Python tool, but keeps the repository aligned with its current shell-script conventions.
  • The release verifier uses python3 -m json.tool for JSON validation because the repo has no package manager and should not add one for 1.2.0.
  • Deferring Claude plugin packaging keeps 1.2.0 focused. The symlink install already covers Claude Code, while Codex plugin packaging is the new release surface.
  • The release verifier now requires the Codex CLI for plugin smoke testing. That makes the release gate less portable, but matches the release claim that the Codex plugin is ready to install.

Open Questions

  • Whether the final release should commit the already-untracked AGENTS.md. The plan leaves it untouched unless the user explicitly approves adding it.
  • Whether to open a PR after the pre-merge audit fix lands. The fix commit will stay on the feature branch; PR creation remains a separate step unless requested.
  • Whether to add Claude plugin packaging in a later release. The plan explicitly defers it from 1.2.0.
